# Limitations

## Synthetic evidence only

All outcomes are generated by `synthetic-dgp-v1`. The project demonstrates
architecture and evaluation discipline, not expected production performance.
The reported rupee values are conditional on the simulator and
`merchant-economics-v1`.

## No causal evidence

The simulator exposes every potential outcome for offline research. The
outcome models are ordinary supervised predictors trained on those synthetic
labels. Real systems observe only the action that was taken and would require
randomized interventions, propensities, or other defensible identification
strategies.

## Current policy does not beat the strongest simple baseline

Always OTP achieves ₹242.31/order on the corrected v2 temporal test split,
while COD Sentinel achieves ₹218.49/order. The DGP makes OTP broadly effective,
and model errors make individualized action selection worse than the simple
policy. The paired customer-cluster bootstrap interval for COD Sentinel minus
the best simple baseline is entirely negative. No post-test tuning was
performed.

## Moderate risk-model discrimination

The held-out COD model has PR-AUC 0.505 at an RTO prevalence of approximately
0.387 in the test period. Calibration is useful for economics, but calibration
does not compensate for limited ranking performance.

## Merchant economics are assumptions

Shipping, payment, refund, margin, inventory damage, and recovery values are
configurable assumptions. Actual contracts may have different fee timing,
refundability, tax, inventory, or operational behavior. Sensitivity analysis
shows predicted policy behavior only; it does not regenerate outcomes.

## Simplified action states

OTP is modeled as a verification step followed by COD. PREPAID includes
abandonment, delivery, and failed delivery/refund. NDR attempts, partial
refunds, exchanges, courier choice, time-to-event, and repeat-contact behavior
are outside the model.

## Pointwise policy evaluation

Historical features come from a fixed synthetic behavior-policy log. Candidate
policies are evaluated pointwise on that context; their selected actions do not
rewrite later customers' histories. Outcomes are now delayed until their
observation time, but this is still not a full sequential policy rollout.

## REVIEW is not modeled economically

REVIEW is only a safety fallback for invalid inputs or unavailable artifacts.
There is no reviewer-accuracy model, service-level agreement, queue, or
economic value-of-information calculation.

## No runtime uncertainty guarantee

The core has calibrated point probabilities but no conformal or frequentist
coverage guarantee. The bootstrap interval in evaluation resamples customers
and applies only to the mean contribution difference.

## No production platform

There is no authentication, database, API service, deployment configuration,
PII handling system, or monitoring. The app is a local competition demo over
synthetic data.

## Optional agent overlay (stretch)

Tab 04 and `make agent-demo` add a live-agent checkout path: address
structuring (Google Geocoding), Hinglish WhatsApp negotiation (Twilio), and
Razorpay payment links. This layer:

- requires live API credentials (`make install-agent` and `.env`)
- is nondeterministic and outside frozen tab 03 evidence
- uses a Streamlit buyer-reply field for inbound WhatsApp in demo mode;
  production would need a webhook
- never reads oracle or latent simulator columns at runtime
